# Whole-product checkpoint — September 24, 2026

## Decision

The model-led brain is credible enough to begin integrating into Growth Operator as a **bounded research-backed input while it continues to improve**. It is not credible enough to act as an autonomous source of proven revenue, conversion or margin conclusions. The claim ledger is the safety boundary: product-scoped source pages and exact quotes can support a visible investigation or leverage recommendation; missing provenance must remain an investigation.

This means the Investigation Lab should not become an open-ended hardening project. The next work should connect its judgment to the existing Snapshot / opportunity / Mission loop.

## What still prevents an unqualified action recommendation

The remaining intelligence weakness is not search coverage. It is the gap between public-source truth and operator economics: GO cannot infer demand, capacity, conversion, margin, ownership or causal impact from a page and a quote. A product claim can be well-sourced and still require a click test, booking data, CRM data or operator confirmation. The current action-plan bridge therefore preserves the claim, evidence IDs, scope and proof requirement, but downgrades unsupported action claims to `INVESTIGATE`.

## What can improve through real product use

Connected booking and analytics data can establish funnel movement; CRM and capacity data can establish economics; customer/operator feedback can improve prioritization and language; mission outcomes can teach GO which recommendations are executable. These are product-learning loops, not reasons to buy more SerpApi searches now. Archived evidence and replay remain sufficient for provenance and regression work.

## Shortest path to the complete GO loop

1. **Understand / Investigate / Judge:** run the bounded research adapter and persist the claim ledger.
2. **Present:** show one primary claim in the existing Snapshot as a research-backed current read, with exact quote, source page, confidence and the proof still needed.
3. **Create a Mission:** map the claim through the action-plan bridge into the existing mission checklist; only validated-provenance claims may appear as action candidates, while others create bounded investigation missions.
4. **Execute / Measure:** use the current bounded checklist and capture baseline, after-state and operator notes in the existing mission completion path; add connectors when available.
5. **Remember / Next opportunity:** persist the claim ID, evidence IDs, mission result and unresolved proof requirement so the next investigation starts from what was learned.

The first integration seam is now implemented: a completed `PROOF_JUDGED` Investigation Lab result can be saved as `growthOperatorResearchJudgment`, opened in the real dashboard, rendered as the source-backed current read, and carried into the existing Mission checklist. The dashboard keeps the claim ID, evidence scope and proof requirement in the finding model and does not fabricate revenue when connected economics are absent. A browser-facing regression covers the handoff and action boundary.

Tomorrow's founder test should use the dashboard experience, not the Lab developer page: run or load a real operator read, inspect the business understanding/current read, open the primary finding, and start the bounded mission. The test should judge whether the operator feels understood and whether the next move is commercially meaningful—not whether the internal evidence machinery is interesting. SerpApi remains exhausted and is intentionally not a blocker for this integration seam; a current live run still requires quota, while archived replay remains valid for the evidence contract.
